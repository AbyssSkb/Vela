# Release signing and publisher trust

[简体中文](release-signing.zh-CN.md)

Platform requirements checked on 2026-11-21. Vela's Ed25519 updater signature authenticates update metadata and the payload it identifies. First installs depend on the trust checks of the receiving platform or distribution channel. [Vela release guide](releasing.md)

| Platform | Current release pipeline | Path for trusted distribution |
| --- | --- | --- |
| Android | Release-key-signed APK for `com.example.vela` | Register the package and existing signer with the device maker or Google, according to the install channel. |
| macOS | Ad-hoc signed `.app` in a DMG and an updater ZIP | Apple Developer ID Application signing and Apple notarization. |
| Windows | Inno Setup `.exe` without Authenticode | Authenticode for the GitHub installer or Microsoft Store signing for a separate MSIX release. |
| Linux | x64 AppImage and an Ed25519-signed update feed | Keep the portable AppImage and add an independently verifiable signature for first downloads if needed. Use a signed package repository for managed installs. |
| iOS and iPadOS | iPad simulator preview in GitHub Actions | Xcode development provisioning for a personal device, TestFlight for a beta, and App Store distribution for general availability. |

The baseline comes from the [package build script](../tool/release/build.sh), [Android Gradle configuration](../android/app/build.gradle.kts), [release feed builder](../tool/release/feeds.py), and [iPad simulator workflow](../.github/workflows/ios-preview.yml).

The public beta.7 and beta.8 APKs both passed APK Signature Scheme v2 verification with certificate SHA-256 `e77c9a0b8c47ac70c4aee4b223c464e3b393cce438a9835542b2b489acb8210b`. The beta.8 Apple Silicon ZIP contains an ad-hoc signed app, and its DMG has no stapled notarization ticket. The Windows installer has no Authenticode certificate table. The Linux AppImage's OpenPGP signature section is empty. These beta.8 assets matched the published checksums. [Public beta.8 files](https://github.com/AbyssSkb/Vela/releases/tag/v0.1.0-beta.8)

## Android

An APK signature lets Android check the package's integrity and signer continuity across versions. Developer verification connects the package and signer to a verified person or organization. For a published APK, run `apksigner verify --verbose --print-certs Vela.apk` and compare its certificate SHA-256 fingerprint with the previous GitHub release. Preserve `com.example.vela` and the existing release key when submitting verification proofs. [APK signing](https://developer.android.com/studio/publish/app-signing) · [apksigner](https://developer.android.com/tools/apksigner)

- **Mainland China ColorOS.** OPPO documents verification of apps installed from outside its store. Complete real-name verification on the OPPO developer platform, claim the app if required, and go to **应用分发 → 应用管理 → 应用验证**. Upload the platform's requested empty proof APK signed with the same key as the production app, confirm the package name and signer, and submit for review. OPPO says approval is reflected in its sideload installer and shared with vivo, Xiaomi, and HONOR. Xiaomi documents its own unverified warning and second confirmation for sideloading. OPPO's guide gives no model-by-model ColorOS coverage or synchronization time. Retest the actual warning on the affected retail device after approval, using the same download source and APK signer. [OPPO verification guide](https://open.oppomobile.com/documentation/page/info?id=13895) · [Xiaomi verification requirements](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2366)
- **Google-certified Android.** Google's September 30, 2026 milestone covers participating app stores in Brazil, Indonesia, Singapore, and Thailand on certified Android 8+ (API 26+) devices. Direct APK downloads are outside that milestone. Google's November 19 update says broader rollout starts in January 2027 with seven app distributors and expands to all installation sources over several months. Google excludes non-certified devices and regions where Google Mobile Services are unsupported. [Google timeline](https://developer.android.com/developer-verification) · [Google verification FAQ](https://developer.android.com/developer-verification/guides/faq) · [November rollout update](https://developer.android.com/blog/posts/android-developer-verification-2027) · [Google Android Help](https://support.google.com/android/answer/17065026)
- **Google registration for Vela.** For public GitHub distribution, use an Android Developer Console Full Distribution account (US$25 registration), verify the developer's identity, and register `com.example.vela` with the SHA-256 certificate fingerprint. Prove ownership with a signed APK containing Google's verification challenge. Request a review if the console flags the existing package or signer as ineligible. The free Limited Distribution account allows up to 50 explicitly authorized devices for personal and test distribution. If Vela also joins Google Play, use Play Console and supply the current signing key to Play App Signing to retain cross-channel update compatibility. [Android Developer Console](https://developer.android.com/developer-verification/guides/android-developer-console) · [Limited Distribution](https://developer.android.com/developer-verification/guides/limited-distribution) · [Play App Signing](https://developer.android.com/studio/publish/app-signing)

Record the precise warning, device model, firmware region and build, and installer or download source before choosing a verification route. Check both a clean install and an in-place upgrade through Vela. Source-permission dialogs and malware checks can still apply. [Google Android developer verification for users](https://support.google.com/android/answer/17065026) · [OPPO verification guide](https://open.oppomobile.com/documentation/page/info?id=13895)

## macOS

Join the Apple Developer Program (US$99/year or local equivalent) for a **Developer ID Application** certificate. In the release packaging step, sign Vela and its nested code, including its share extension and Sparkle helpers, after adding the third-party notices. Preserve the appropriate entitlements and use hardened runtime and a secure timestamp. Submit the signed `.app` in a temporary ZIP to `notarytool`, wait for acceptance, and staple the ticket to the `.app`. Build the public DMG and Sparkle update ZIP from that app. Sign, notarize, and staple the DMG too. Generate the existing update signatures and checksums after the files are final. [Apple enrollment](https://developer.apple.com/help/account/membership/program-enrollment/) · [Distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/) · [Apple notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow) · [Sparkle update signing](https://sparkle-project.org/documentation/publishing/)

Use `codesign --verify --deep --strict`, `xcrun stapler validate`, and `spctl --assess --type execute --verbose=4` on the relevant artifacts. Test a quarantined DMG downloaded on a clean Mac and a Sparkle upgrade from the latest published ad-hoc build. Preserve bundle IDs and test whether the signing identity change affects Keychain access, the sandbox container, sharing, or device identity. [Apple notarization troubleshooting](https://developer.apple.com/documentation/security/resolving-common-notarization-issues) · [Code signing requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) · [Sandbox access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox) · [Vela packaging script](../packaging/macos/package.sh)

## Windows

For the existing GitHub release, first assess **SignPath Foundation**. Vela's MIT license and publicly released Inno installer make it a candidate. Admission is subject to review of the project and pipeline. The certificate displays SignPath Foundation as publisher. Its terms require verifiable source builds, per-release manual approval, multifactor authentication, and a public signing policy. Review its rules for bundled third-party DLLs before submitting. As alternatives, Microsoft's Azure Artifact Signing Public Trust starts around US$9.99/month, with individual accounts limited to the United States and Canada and organization accounts supported in those countries, the EU, and the UK. A publicly trusted OV certificate is another option when the Azure region limits exclude the publisher. [SignPath Foundation terms](https://signpath.org/terms) · [Microsoft signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options) · [Vela license](../LICENSE)

Sign the Vela executable and applicable first-party DLLs before packing. Use Inno Setup's signing integration to cover the uninstaller and setup executable. Use SHA-256 with an RFC 3161 timestamp, then verify the final files with `signtool verify /pa /v /tw` on Windows. Preserve the Inno `AppId` and test upgrading an existing install. SmartScreen also considers file and publisher reputation, so a newly signed download can still warn, including with an EV certificate. [Inno Setup signing](https://jrsoftware.org/inno-setup/documentation/topic_setup_signtool.htm) · [Authenticode timestamps](https://learn.microsoft.com/en-us/windows/win32/seccrypto/time-stamping-authenticode-signatures) · [SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool) · [SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) · [Vela installer](../packaging/windows/vela.iss)

The Microsoft Store can sign an **MSIX** submission for free and manage updates for Store installs. Its existing EXE/MSI submission path requires the publisher to sign the installer. A standalone GitHub MSIX needs its own trusted signature, and automatic updates require a stable `.appinstaller` URL or a Store install. Treat MSIX as a packaging migration. Verify data and pairing identity migration from Inno, notifications, autostart, and which updater is active for each install. [Microsoft signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options) · [App Installer updates](https://learn.microsoft.com/en-us/windows/msix/app-installer/app-installer-file-overview) · [MSIX conversion considerations](https://learn.microsoft.com/en-us/windows/msix/packaging-tool/know-your-installer)

## Linux

Keep shipping the existing AppImage for portable installs. AppImage tooling can embed an OpenPGP signature. Initial downloads still need a trusted copy of the public key and signature verification by a tool that supports it. For managed installation, consider Flathub. It distributes through a signed Flatpak remote, and Vela can apply for publisher verification for `io.github.abyssskb.vela` using the GitHub repository owner. Test sandbox permissions for discovery and receiving, desktop notifications, tray behavior, and file access. Let Flatpak manage updates on that channel. [AppImage signatures](https://docs.appimage.org/packaging-guide/optional/signatures.html) · [Flatpak repository signing](https://docs.flatpak.org/en/latest/hosting-a-repository.html) · [Flathub publisher verification](https://docs.flathub.org/docs/for-app-authors/verification) · [Vela Linux packaging](../packaging/linux/package.sh)

## iOS and iPadOS

Use Xcode's **Personal Team** to test on your own connected iPhone or iPad with Developer Mode and an available bundle ID. Free provisioning expires after seven days. For general beta testing, the Apple Developer Program membership used for macOS also supports TestFlight. Each build lasts up to 90 days. The first external build goes to beta review, and TestFlight supports up to 10,000 external testers. Ad Hoc distribution is for registered devices, with up to 100 per product family per membership year. Use App Store Connect and App Review for general public distribution. Apple supports other channels in specific regions under separate requirements. [Personal Team](https://developer.apple.com/help/account/basics/about-your-developer-account/) · [Developer Mode](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device) · [Apple Developer Program](https://developer.apple.com/programs/) · [TestFlight](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/) · [Ad Hoc devices](https://developer.apple.com/help/account/devices/devices-overview) · [Regional alternative distribution](https://developer.apple.com/documentation/marketplacekit/participating-in-alternative-distribution-for-specific-regions)
