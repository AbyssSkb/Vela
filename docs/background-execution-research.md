# Background receiving

[简体中文](background-execution-research.zh-CN.md)

Background receiving requires a running Vela node that can connect to its peer. Test app backgrounding, system sleep, process reclamation, user-initiated quit, and recovery after reboot separately. Use an actual receive to verify each scenario. [User guide](user-guide.md#receive-in-the-background)

## Current implementation

| Platform | How Vela stays available |
| --- | --- |
| Android | With background receiving enabled, `ReceivingService` runs as a foreground service, posts a notification, and holds a partial wake lock. When the system recreates the sticky service, it reads the saved setting. When Android delivers `BOOT_COMPLETED` after the first unlock, `BootReceiver` uses the same setting to start the service. |
| macOS | Closing the window keeps the process and menu-bar entry available. The optional **Keep available in background** setting prevents idle system sleep. On macOS 13 or later, users can configure a separate system-managed login item. Network and wake events notify Flutter to recover the node and reachability state. |
| Windows and Linux | With background receiving enabled and a tray available, the app stays in the tray after its window closes. The desktop integration coordinates windows, notifications, and quitting. |

Android's receiving service can start the shared FlutterEngine without a foreground Activity. macOS checks background availability and launch-at-login state separately. [ReceivingService.kt](../android/app/src/main/kotlin/com/example/vela/ReceivingService.kt) · [BootReceiver.kt](../android/app/src/main/kotlin/com/example/vela/BootReceiver.kt) · [AppDelegate.swift](../macos/Runner/AppDelegate.swift) · [MainFlutterWindow.swift](../macos/Runner/MainFlutterWindow.swift)

## Android system constraints

- **Foreground service.** Vela declares `specialUse`. `START_STICKY` lets Android try to recreate the service after reclaiming its process. The callback can carry a null Intent. On Android 12 and later, apps targeting API 31 or higher face restrictions on new foreground-service starts from the background. System restarts of sticky foreground services are exempt. [Service API](https://developer.android.com/reference/android/app/Service#START_STICKY) · [Background startup restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start) · [Service types](https://developer.android.com/develop/background-work/services/fgs/service-types)
- **Reboot.** Android delivers `BOOT_COMPLETED` after the first unlock. This permits starting Vela's `specialUse` service and loading the existing identity and pairing data from credential-encrypted storage. That storage stays available during later screen locks. On Android 13 and later, setting background battery usage to **Restricted** can postpone both boot broadcasts until the app starts for another reason if it targets API 33 or higher. [Direct Boot](https://developer.android.com/privacy-and-security/direct-boot) · [Boot broadcast](https://developer.android.com/reference/android/content/Intent#ACTION_BOOT_COMPLETED) · [Boot service restrictions](https://developer.android.com/about/versions/15/behavior-changes-15#fgs-boot-completed) · [Restricted battery usage](https://developer.android.com/about/versions/13/behavior-changes-13#battery-resource-utilization)
- **Auto-start settings.** Vela links to the system settings that manage auto-start. The boot receiver starts background receiving when Android delivers the boot broadcast and the user has enabled background receiving. [Boot receiver](../android/app/src/main/kotlin/com/example/vela/BootReceiver.kt)
- **User stop.** The Android **Active apps** stop action ends the process. **Force stop** in system app settings also places the app in a stopped state until the user interacts with it again. Receiving can stop after an explicit user stop. Test task dismissal, system reclamation, user stop, and reopening separately. [Stopping an app with a foreground service](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping) · [Android 15 stopped state](https://developer.android.com/about/versions/15/behavior-changes-all#enhanced-stop-states)
- **Screen lock and Doze.** A partial wake lock can keep the CPU awake while the display is off. On battery, Android can restrict the network after screen-off in light Doze and ignore wake locks in deep Doze. The system battery-optimization exemption permits network access and partial wake locks during Doze. The user can grant it in Android settings, and `isIgnoringBatteryOptimizations()` reports whether it is active. [Partial wake lock](https://developer.android.com/reference/android/os/PowerManager#PARTIAL_WAKE_LOCK) · [Platform Doze behavior](https://source.android.com/docs/core/power/platform_mgmt#detection) · [Doze exemptions](https://developer.android.com/training/monitoring-device-state/doze-standby#support_for_other_use_cases)
- **Battery optimization settings.** Selecting the exemption row asks Android to show its confirmation for Vela. The Android exemption list remains available if the app is already exempt or the device does not handle the confirmation. App details are a separate entry for background activity restrictions. [Android Doze exemptions](https://developer.android.com/training/monitoring-device-state/doze-standby#support_for_other_use_cases)
- **Network recovery.** Android 10 and later report when a network becomes accessible again through `onBlockedStatusChanged`. Vela uses the unblocked default network as a signal to refresh peer reachability through the existing network-change path. [Network callback](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback#onBlockedStatusChanged(android.net.Network,%20boolean)) · [VelaApplication.kt](../android/app/src/main/kotlin/com/example/vela/VelaApplication.kt)
- **Low Power Standby.** When enabled, this independent policy can suspend network access and ignore wake locks for apps, including foreground services, while the device is non-interactive outside maintenance windows. Record whether the device enables it and whether Vela is exempt. [PowerManager](https://developer.android.com/reference/android/os/PowerManager#isLowPowerStandbyEnabled())
- **Incoming notifications.** On Android 13 or later, notification permission controls whether incoming offers appear. The foreground service can run with notifications denied. The system's lock-screen notification settings also control what the user can see while locked. [Notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission) · [Lock-screen visibility](https://developer.android.com/develop/ui/views/notifications/build-notification#lockscreenNotification)
- **Scheduling and push.** When an app targets Android 15 or higher, `dataSync` and `mediaProcessing` foreground services each get six cumulative background hours per 24 hours. `dataSync` also has boot startup restrictions. WorkManager is for deferrable tasks. High-priority FCM suits timely user-visible notifications. Adding it would require evaluating infrastructure, coverage, and system constraints. [Foreground service timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout) · [Android 15 behavior changes](https://developer.android.com/about/versions/15/behavior-changes-15#fgs-boot-completed) · [FCM priority](https://firebase.google.com/docs/cloud-messaging/android-message-priority)

### OnePlus 13 (ColorOS, China)

Use Normal power mode for the baseline. ColorOS 15 and later can limit background activity, disable background sync, and remove Recents locks in Power Saving mode. ColorOS lists the OnePlus 13 in the rollout for its 2025 Recents locking improvements. [OPPO power-saving settings](https://support.oppo.com/cn/answer/?aid=SI2105920) · [ColorOS rollout](https://www.coloros.com/article/A00000102/)

Huawei Health's guide for OPPO phones shows two per-app controls under **应用耗电管理**. Check for **允许完全后台行为** when testing screen lock and **允许应用自启动** when testing reboot. Confirm the labels and behavior for Vela on the installed ColorOS build. Verify whether it receives the boot broadcast and can accept a transfer after the first unlock. [OPPO settings for Huawei Health](https://consumer.huawei.com/cn/support/content/zh-cn15848664/)

Check ColorOS background activity after granting the Doze exemption. `isBackgroundRestricted()` reports restrictions exposed by Android's API. A `false` result does not report the vendor's smart optimization mode. Leave the Doze exemption in place and compare screen-locked receipt with smart optimization and with all background activity allowed. Record process and foreground service state alongside receipt from the same paired sender. If the process exits, check `adb shell dumpsys activity exit-info com.example.vela`. [Android background restriction API](https://developer.android.com/reference/android/app/ActivityManager#isBackgroundRestricted()) · [ColorOS settings walkthrough](https://gsxnj.cn/help/android/background-running-oppo/) · [Don’t Kill My App’s OPPO guide](https://dontkillmyapp.com/oppo)

Other vendors expose different controls. Xiaomi documents **No restrictions** for apps whose network access is limited after screen lock. Samsung documents automatic sleeping and the **Never sleeping apps** list. Record the actual vendor settings alongside the Android battery-optimization exemption. [Xiaomi 15 support](https://www.mi.com/global/support/faq/details/KA-538010/) · [Samsung app management](https://developer.samsung.com/mobile/app-management.html)

## macOS system constraints

App Nap affects timers and resource scheduling for apps that are offscreen. Test actual receipt while the menu-bar icon is present. Record screen-off, idle system sleep, manual sleep, and lid closure separately. The activity that prevents idle sleep applies to idle system sleep. The login item using `SMAppService.mainApp` takes effect on a subsequent login and is controlled by system settings. [App Nap](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/AppNap.html) · [Sleep and power assertions](https://developer.apple.com/library/archive/qa/qa1340/_index.html) · [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)

## Verification

For the OnePlus 13, test on battery and record the ColorOS build, network path, per-app settings, and time spent with the screen off. Change one power setting at a time when comparing results.

| Scenario | What to check and record |
| --- | --- |
| Background, short and long screen lock | Send text and a file after both a short lock and extended idle. Record offer arrival, notification visibility, acceptance, transfer completion, and latency. |
| Android Doze and Low Power Standby | Test each restriction on an isolated device. Record system state, exemptions, receipt, and recovery after leaving that state. [Doze test procedure](https://developer.android.com/training/monitoring-device-state/doze-standby#testing_doze) |
| Android reboot | Enable background receiving, reboot, and unlock the phone without opening Vela. Send an offer from an already paired peer and verify receipt with the same identity. Repeat with background receiving disabled and check that the service stays stopped. |
| Android system reclamation and user stop | Check that the service and node recover after system reclamation. Record the effect of Recents dismissal and intentional stops separately, then confirm receiving works again after manually opening Vela. |
| macOS App Nap, lid close, and wake | Record visible windows, the menu bar, sleep, and wake separately. Use `pmset -g assertions` to check idle-sleep assertions. |
| Windows/Linux tray and sleep | Restore the app from the tray after closing the window. Test notification approval and reconnection after sleep or logout. |
| Resource cost | Under the same network and power conditions, compare battery use, CPU, network traffic, and receiving latency with background receiving on and off. |

An Android 35 emulator run on 2026-11-10 recorded the sticky service rebuilding the engine and node after process termination and receiving text and a file. Record results against the new candidate. Use an isolated device for changes to battery, sleep, or login settings and restore the settings after the test. [Release acceptance checklist](launch-checklist.md)
